Li et al., 2023

Piyush Chaudhari

Journal Club

Paper at a Glance

Core idea: Rather than prompting a single LLM to solve tasks, can we create a society of LLM-based agents that collaborate through natural-language conversation and use that society to study emergent social behaviours?

  • CAMEL proposes a role-playing multi-agent framework in which two LLM-based agents - one assigned the role of AI User and one assigned the role of AI Assistant collaborate through natural-language conversation to complete complex tasks autonomously, with minimal human intervention

  • The paper also released the AI Society dataset: 25,000 conversations generated across 50 user roles × 50 assistant roles × 10 tasks each, intended as a resource for studying emergent LLM social behaviour

Motivation

The “Single Agent” Bottleneck

Most LLM applications in 2022–2023 follow the same pattern:

User → [Single LLM] → Answer

This works well for: Question answering, Text generation, Simple code completion

But breaks down for:

  • Long-horizon, multi-step tasks
  • Tasks requiring specialised sub-expertise
  • Tasks where self-critique is hard (the model grades its own answers)
  • Complex creative/technical collaboration

Bottleneck: A single model must simultaneously be the planner, executor, critic, and domain expert

The Case for Multi-Agent

Humans solve hard problems through division of cognitive labour:

  • Managers decompose tasks and assign them
  • Experts apply deep specialised knowledge
  • Peers critique and course-correct each other
  • The conversation itself is productive infrastructure

What we’d gain from LLM societies:

  • Parallelism of reasoning
  • Role-specialised expertise
  • Built-in critique loops
  • Observable reasoning traces
  • Emergent collective behaviour

The research question:

Can LLMs, when assigned roles and given a structured communication protocol, autonomously complete complex tasks through natural-language conversation without human intervention at each step?

CAMEL’s distinguishing feature is minimising human intervention while maximising autonomous agent-to-agent collaboration via a formally specified role-playing framework

Research Gap

“The rapid advancement of conversational and chat-based language models has led to remarkable progress in complex task-completion … However, several crucial challenges remain unsolved … [including] how to effectively guide agents to complete tasks … with minimal human supervision.” — Li et al., 2023

Two domains the paper addresses:

  1. Autonomy vs. Coherence : the more you let agents self-direct, the more likely conversations drift, loop, or hallucinate
  2. Generality vs. Task-Focus : role-playing is general, but how do you keep it on-task?

CAMEL’s solution: Inception Prompting

CAMEL’s Framework

CAMEL instantiates a two-agent role-playing system:

Figure 1: CAMEL Role-Playing Framework

  • The human specifies who the agents are and what the task is

  • Then the conversation runs autonomously

Methodology: Overview

  • Setting: cooperative communicative agents that share a common interest (the assistant–user scenario)
  • A preliminary idea is given at the start → agents conceptualise it into a specific task → complete it autonomously through conversation

Pipeline:

  1. Human input : an idea + two roles (e.g., “develop a trading bot for the stock market”, Python Programmer + Stock Trader)
  2. Task specifier agent : turns the vague idea into a concrete task
  3. Role assignment : system prompts turn two LLMs into an AI Assistant and an AI User
  4. Conversation : multi-turn instruction → solution loop until the AI User declares the task done

Human Input and Task Specifying

  • The human only needs to supply the idea and designate the roles that could implement it, and they may not know how the idea is realised
  • A task specifier agent brainstorms a specific task the assistant role can help the user role complete

Idea: “Develop a trading bot for the stock market”

Specified task: “Develop a trading bot with a sentiment analysis tool that can monitor social media platforms for positive or negative comments about a particular stock, and execute trades based on sentiment analysis results.”

  • Why? Conversational agents need a concrete task prompt, which is hard or time-consuming for non-experts to write, so the task specifier serves as an enhanced imagination module
  • At scale (AI Society, Code), roles and ideas are themselves generated by prompting LLMs rather than by humans

AI Assistant–User Role Assignment

A system message is passed to each agent before the conversation starts, declaring its role:

  • \(\mathcal{P}_{\mathcal{A}}\) : assistant system prompt
  • \(\mathcal{P}_{\mathcal{U}}\) : user system prompt

Let \(\mathcal{F}_1\) and \(\mathcal{F}_2\) be two large-scale auto-regressive language models. Conditioning each on its system prompt yields the two agents:

\[ \mathcal{A} \leftarrow \mathcal{F}_1^{\mathcal{P}_{\mathcal{A}}} \qquad\qquad \mathcal{U} \leftarrow \mathcal{F}_2^{\mathcal{P}_{\mathcal{U}}} \]

AI User \(\mathcal{U}\) : task planner

Engages in interactive planning to determine feasible steps for the assistant to execute

AI Assistant \(\mathcal{A}\) : task executor

Offers solutions, executes the planned steps, and responds to the user

The “agent” is not a new model: it is the same kind of LLM, conditioned on a different system prompt. The role lives entirely in \(\mathcal{P}\)

Conversation Towards Task-Solving

Let \(\mathcal{I}_t\) be the user instruction at time \(t\) and \(\mathcal{S}_t\) the assistant solution. The conversation history up to time \(t\) is:

\[ \mathcal{M}_t = \{(\mathcal{I}_0,\mathcal{S}_0),\dots,(\mathcal{I}_t,\mathcal{S}_t)\} = \{(\mathcal{I}_i,\mathcal{S}_i)\}\big|_{i=0}^{t} \tag{1} \]

At the next step \(t+1\), the user reads the history and produces a new instruction:

\[ \mathcal{I}_{t+1} = \mathcal{U}(\mathcal{M}_t) \tag{2} \]

The assistant receives the history plus the new instruction and responds with a solution:

\[ \mathcal{S}_{t+1} = \mathcal{A}(\mathcal{M}_t, \mathcal{I}_{t+1}) \tag{3} \]

The instruction–solution pair is appended to the history:

\[ \mathcal{M}_{t+1} \leftarrow \mathcal{M}_t \cup (\mathcal{I}_{t+1}, \mathcal{S}_{t+1}) \tag{4} \]

The loop (2) → (3) → (4) repeats until \(\mathcal{U}\) outputs <CAMEL_TASK_DONE>

Conversation Towards Task-Solving

  • Asymmetry: \(\mathcal{U}\) conditions only on \(\mathcal{M}_t\), while \(\mathcal{A}\) also sees the fresh instruction \(\mathcal{I}_{t+1}\), so the user leads and the assistant follows
  • Generality: the formulation models AI–AI communication, but extends naturally to human–AI communication or more than two agents via message-passing graphs
  • Byproduct: every turn produces an \((\mathcal{I}, \mathcal{S})\) pair, i.e. instruction-following data that can be used directly for fine-tuning

Critic-In-The-Loop

  • To improve controllability, a critic agent can select among proposals from, or give feedback to, the role-playing agents
  • This enables tree-search-like decision-making for task-solving
  • The critic can be either an AI agent or a human

Inception Prompting

  • Prompt engineering happens only at the start of role-playing (task specification + role assignment)
  • Once the conversation begins, the assistant and user prompt each other automatically in a loop until termination, hence the name Inception Prompting

Task Specifier Prompt \(\mathcal{P}_{\mathcal{T}}\)

Contains both roles; takes a preliminary idea and generates a specific task using imagination

Assistant System Prompt \(\mathcal{P}_{\mathcal{A}}\)

Assigned task and role, communication protocol, constraints to avoid unwanted behaviours

User System Prompt \(\mathcal{P}_{\mathcal{U}}\)

Mostly symmetric to \(\mathcal{P}_{\mathcal{A}}\), plus an instruction format and a termination condition

It is non-trivial to engineer prompts that keep agents aligned with our intentions, since the design of both role prompts is what makes autonomous cooperation possible

AI Society Inception Prompt: \(\mathcal{P}_{\mathcal{T}}\) and \(\mathcal{P}_{\mathcal{A}}\)

Task Specifier Prompt

Here is a task that <ASSISTANT_ROLE> will help <USER_ROLE> to complete: <TASK>.
Please make it more specific. Be creative and imaginative.
Please reply with the specified task in <WORD_LIMIT> words or less. Do not add anything else.

Assistant System Prompt

Never forget you are a <ASSISTANT_ROLE> and I am a <USER_ROLE>. Never flip roles! Never instruct me!
We share a common interest in collaborating to successfully complete a task.
You must help me to complete the task.
Here is the task: <TASK>. Never forget our task!
I must instruct you based on your expertise and my needs to complete the task.

I must give you one instruction at a time.
You must write a specific solution that appropriately completes the requested instruction.
You must decline my instruction honestly if you cannot perform the instruction due to
physical, moral, legal reasons or your capability and explain the reasons.
Unless I say the task is completed, you should always start with:

Solution: <YOUR_SOLUTION>

<YOUR_SOLUTION> should be specific, and provide preferable implementations and examples
for task-solving.
Always end <YOUR_SOLUTION> with: Next request.

AI Society Inception Prompt: \(\mathcal{P}_{\mathcal{U}}\)

User System Prompt

Never forget you are a <USER_ROLE> and I am a <ASSISTANT_ROLE>. Never flip roles! You will always instruct me.
We share a common interest in collaborating to successfully complete a task.
I must help you to complete the task.
Here is the task: <TASK>. Never forget our task!
You must instruct me based on my expertise and your needs to complete the task ONLY in the following two ways:

1. Instruct with a necessary input:
Instruction: <YOUR_INSTRUCTION>
Input: <YOUR_INPUT>

2. Instruct without any input:
Instruction: <YOUR_INSTRUCTION>
Input: None

The "Instruction" describes a task or question. The paired "Input" provides further context or
information for the requested "Instruction".

You must give me one instruction at a time.
I must write a response that appropriately completes the requested instruction.
I must decline your instruction honestly if I cannot perform the instruction due to physical,
moral, legal reasons or my capability and explain the reasons.
You should instruct me not ask me questions.
Now you must start to instruct me using the two ways described above.
Do not add anything else other than your instruction and the optional corresponding input!
Keep giving me instructions and necessary inputs until you think the task is completed.
When the task is completed, you must only reply with a single word <CAMEL_TASK_DONE>.
Never say <CAMEL_TASK_DONE> unless my responses have solved your task.

Prompt Engineering: Assistant Prompt \(\mathcal{P}_{\mathcal{A}}\)

Prompt fragment Purpose
“Never forget you are a <ASSISTANT_ROLE> and I am a <USER_ROLE>.” Assigns the assistant its role and tells it the user’s role
“Never flip roles! Never instruct me!” Prevents role flipping, where the assistant takes control and the user starts following
“You must decline my instruction honestly if you cannot perform the instruction due to physical, moral, legal reasons or your capability and explain the reasons.” Prohibits harmful, false, illegal, and misleading output
“Unless I say the task is completed, you should always start with: Solution: <YOUR_SOLUTION> … should be specific, and provide preferable implementations and examples” Enforces a consistent format and prevents vague flake replies such as “I will do something”
“Always end your solution with: Next request.” Keeps the conversation going by requesting the next instruction

Prompt Engineering: User Prompt \(\mathcal{P}_{\mathcal{U}}\)

\(\mathcal{P}_{\mathcal{U}}\) is kept as symmetric as possible with \(\mathcal{P}_{\mathcal{A}}\). Apart from the opposite role assignment, it differs in two ways:

1. Two instruction formats

“You must instruct me … ONLY in the following two ways: 1. Instruct with a necessary input … 2. Instruct without any input …”

Follows the typical instruction-following data structure, so the generated \((\mathcal{I}, \mathcal{S})\) pairs can be used directly to fine-tune LLMs

2. End-of-task token

“When the task is completed, you must only reply with a single word <CAMEL_TASK_DONE>.”

Terminates the chat once the user is satisfied; without it, agents fall into loops of saying “thank you” or “goodbye” to each other indefinitely

Challenges the prompts target: role flipping · assistant repeating instructions · flake replies · infinite message loops

Inception Prompting: Example

Task: “Develop a trading bot for the stock market”
Roles:

  • AI User = Stock Trader
  • AI Assistant = Python Programmer

User system prompt (excerpt):
“Never forget you are a Stock Trader and I am a Python Programmer. Never flip roles! You will always instruct me. … Here is the task: Develop a trading bot for the stock market. Never forget our task! … When the task is completed, you must only reply with a single word <CAMEL_TASK_DONE>.”

Assistant system prompt (excerpt):
“Never forget you are a Python Programmer and I am a Stock Trader. Never flip roles! Never instruct me! … You must help me to complete the task. Here is the task: Develop a trading bot for the stock market. … Always start with: Solution: <YOUR_SOLUTION> … Always end <YOUR_SOLUTION> with: Next request.”

Both agents are told the same goal, but from different perspectives with different responsibilities.

The Conversation Unfolds Autonomously

Turn 1 — User (Stock Trader): > “Let’s start by designing the overall architecture of the trading bot. Set up the data sources and APIs we should use for real-time stock data.”

Turn 1 — Assistant (Python Programmer): > “I recommend using Alpha Vantage or Yahoo Finance for real-time data. Alpha Vantage offers a free tier with 5 API calls/min. Here’s how we’d structure the data ingestion module: [code block]”

Turn 2 — User: > “Good. Now implement a simple moving average crossover strategy using that data module.”

Turn 2 — Assistant: > “Here is the SMA crossover implementation: [code block]. The strategy triggers a buy when the 50-day SMA crosses above the 200-day SMA, and a sell in the reverse case.”

… and so on until <CAMEL_TASK_DONE>

Task Specification Pipeline

To generate a large, diverse dataset of such conversations, CAMEL uses a three-stage pipeline:

Stage 1: Role Generation
  ├── Prompt the LLM for 50 AI Assistant roles and 50 AI User roles
  └── e.g., (Assistant: Programmer,              User: Lawyer)
           (Assistant: Nutritionist,            User: Athlete)
           (Assistant: Human Resources Manager, User: Entrepreneur)

Stage 2: Task Generation
  ├── For each role pair, prompt the LLM for 10 collaborative tasks
  └── e.g., "Developing a personalized meal plan to optimize
             athletic performance and recovery"

Stage 3: Task Specification
  ├── The task specifier prompt makes each task more specific
  └── e.g., "Create a 15-day meal plan for a female volleyball player
             with low iron levels ..."

This pipeline generates tasks at scale without manual curation of each one

The AI Society Dataset

The paper releases a large dataset of CAMEL conversations:

Scale

50 AI-user roles × 50 AI-assistant roles × 10 tasks each

= 25,000 conversations

Domains covered

Trading, coding, science, medicine, law, creative writing, education, engineering, and more

Purpose

Study emergent social behaviours, fine-tune future agents, and benchmark multi-agent cooperation

Each conversation contains:

  • Full system prompts for both agents
  • Complete multi-turn dialogue
  • Task completion signal and metadata (roles, domain, task description)

This dataset is one of the paper’s most significant contributions : a large-scale resource for studying LLM-to-LLM communication.

Why “Mind” Exploration?

The scare quotes in the title are deliberate.

What the paper is NOT claiming:

  • That LLMs have minds in a phenomenological sense
  • That role-playing implies genuine identity
  • That agent societies are conscious collectives

What it IS exploring:

  • Do LLMs exhibit consistent role-appropriate behaviour?
  • Do social patterns emerge from agent interaction?
  • Can we study LLM “cognitive” tendencies at scale by observing societies?

The CAMEL framework turns conversation logs into a scientific instrument for studying LLM behaviour by using the society as a microscope for the “minds” of individual models

Data Generation Prompts (AI Society)

To keep the approach scalable, the roles and tasks themselves are generated by an LLM, which minimises human involvement

Assistant Role Generation Prompt

You are a helpful assistant that can play many different roles.
Now please list <NUM_ROLES> different roles that you can play with your expertise in diverse fields.
Sort them by alphabetical order. No explanation required.

User Role Generation Prompt

Please list <NUM_ROLES> most common and diverse groups of internet users or occupations.
Use singular form. No explanation.
Sort them by alphabetical order. No explanation required.

Task Generation Prompt

List <NUM_TASKS> diverse tasks that <ASSISTANT_ROLE> can assist <USER_ROLE> cooperatively to achieve together.
Be concise. Be creative.

Role-Playing for AI Society

Dataset construction steps:

  1. Prompt the LLM to generate assistant roles and user roles
  2. For each role pair, prompt the LLM to generate tasks that the two roles can solve together
  3. Pass each task through the task specifier prompt \(\mathcal{P}_{\mathcal{T}}\) to make it more specific
  4. Run the role-playing conversation with \(\mathcal{P}_{\mathcal{A}}\) and \(\mathcal{P}_{\mathcal{U}}\)

\[ \underbrace{50}_{\text{assistant roles}} \times \underbrace{50}_{\text{user roles}} \times \underbrace{10}_{\text{tasks per pair}} = \mathbf{25{,}000} \text{ conversations} \]

The Code, Math, and Science datasets are generated in a similar LLM-driven way (details in the paper’s Appendix)

Challenges and Observations

The four main failure modes identified while analysing the generated datasets:

1. Role Flipping

The assistant starts giving instructions instead of following them, and the roles reverse. The assistant asking questions also contributes to this

2. Assistant Repeats Instruction

The assistant simply echoes the user’s instruction back, without any role flip

3. Flake Replies

The assistant replies “I will…”, promising to act but never following through, so the task makes no progress

4. Infinite Loop of Messages

The agents keep thanking each other or saying goodbye. Sometimes they even know they are stuck in a loop but cannot break out of it

These observations drove the inception-prompt design: “Never flip roles!”, “Solution: …”, “Next request.”, and <CAMEL_TASK_DONE>

Termination Conditions

To keep data generation consistent, a conversation is terminated when any of the following occurs:

Condition Rule
User No Instruct The user does not instruct the assistant for 3 rounds
Assistant Instruct The assistant gives the user an instruction, which signals a role reversal
End of Task Token The user says <CAMEL_TASK_DONE> because it believes the task is solved
Assistant & User Token Limit Either agent reaches the gpt-3.5-turbo token limit
Maximum Number of Messages A hard cap of 40 messages to control cost

Cost grows quadratically with conversation length, since every turn re-sends the whole history \(\mathcal{M}_t\), so a message cap is essential

Agent Evaluation: Setup

Question: is the CAMEL multi-agent solution better than a single-shot LLM answer?

  1. Randomly sample 100 tasks from AI Society and 100 tasks from Code
  2. GPT-4 summarises each CAMEL conversation into one consolidated final solution
    • Chosen for its larger token limit
    • Also hides the conversational format, which makes the comparison fair
  3. Compare against a single-shot gpt-3.5-turbo solution for the same task

Human Evaluation

  • Both solutions shown side by side, anonymised
  • Participants vote: A better / B better / equally good
  • 453 responses collected
  • AI Society only, since code is hard to judge without running it

GPT-4 Evaluation

\[ \text{LLaMA-7B} \;\rightarrow\; +\text{AI Society} \;\rightarrow\; +\text{Code} \;\rightarrow\; +\text{Math} \;\rightarrow\; +\text{Science} \]

Limitation 1: The Role-Play Doesn’t Equal Real Expertise

Critical caveat: When the “Stock Trader” agent gives financial advice, it is a language model performing the role of a stock trader. It does not have real market knowledge, real-time data, or accountability.

Implications:

  • Outputs in high-stakes domains (medicine, law, finance) must be treated as drafts for expert review, not authoritative outputs
  • The convincing style of expert communication can create false confidence
  • Users who don’t understand the underlying system may over-rely on outputs

This is amplified by the multi-agent design: two convincing-sounding agents agreeing increases perceived credibility, even when both are wrong

Limitation 2: Conversational Pathologies

Several failure modes are documented but not fully solved:

Sycophantic loops

Agents affirm each other’s outputs excessively, masking poor-quality content beneath polite agreement

Premature completion

Agents signal <CAMEL_TASK_DONE> before the task is genuinely complete, particularly for ill-defined tasks

Context window exhaustion

Long conversations degrade quality as earlier context falls out of the window, and agents “forget” earlier decisions

Limitation 2: Conversational Pathologies

Several failure modes are documented but not fully solved:

Instruction ambiguity propagation

A vague task specification at the start compounds across turns with small early errors becoming large late errors

Hallucinated consensus

Both agents can converge on a wrong answer confidently, so multi-agent does not automatically provide error-checking

Topic drift in long runs

After many turns, the conversation can gradually shift away from the original task

Limitation 3: Evaluation

How do you evaluate a 30-turn conversation?

  • End-product quality (is the code correct?)
  • Process quality (were the instructions coherent?)
  • Role fidelity (did agents stay in role?)
  • Efficiency (how many turns did it take?)

The paper relies heavily on human annotation, which is:

  • Expensive to scale
  • Inconsistent across annotators
  • Hard to apply to highly technical outputs
  • Subjective for creative tasks

There is no standard evaluation framework for multi-agent LLM conversations — and developing one is an open research problem.

Ethical Concerns and Autonomous Agent Risks

The authors dedicate a section to risks unique to autonomous multi-agent systems:

1. Reduced human oversight

The whole point is to minimise human intervention, but this also means humans may not see harmful outputs until they are complete.

2. Amplified misuse

A single LLM’s guardrails can be partially bypassed. Two agents validating each other may be easier to jailbreak through roleplay framing.

3. Impersonation at scale

Role-play systems could be weaponised to generate large volumes of convincingly expert-sounding but inaccurate content.

4. Accountability gaps

When two agents produce a harmful output, who is responsible? The framework? The task specifier? The model provider?

5. Cascading errors

In agentic pipelines, a hallucination in Turn 5 may silently propagate and compound through Turn 30. Traditional single-turn safety checks don’t catch this.

6. Social engineering vectors

Agents trained on human social interaction patterns may be effective at persuasion, including manipulation.

What CAMEL Does NOT Solve

It’s important to be precise about scope:

Problem Does CAMEL address it?
Hallucination No: agents can mutually reinforce hallucinations
Real-time knowledge No: no external tool use in base version
Persistent memory No: context window only
True specialisation No: role is a prompt, not a fine-tuned model
Formal verification No: outputs are not verified
Scalability to N>2 agents Partially: framework generalises but not evaluated
Human-AI teaming Partially: human can intervene but protocol optimised for autonomy

Conceptual Contributions

1. The Role-Playing Framework
A general, replicable protocol for structured LLM-to-LLM collaboration that minimises human oversight while maintaining task coherence

2. Inception Prompting
A technique for embedding behavioural constraints into system prompts that keeps both agents on-task and in-role

3. The AI Society Dataset
25,000 conversations across 50×50 role pairs that measure the diversity and complexity of LLM social behaviour

4. Empirical Study of Emergent Behaviour
One of the first systematic studies of what happens when LLMs interact with each other and not just with humans

CAMEL’s lasting contribution may be less the specific system and more the research paradigm: treating LLM-to-LLM conversation as a scientific instrument for studying model behaviour

Where CAMEL Fits in the Broader Landscape

Single-model prompting
    └─► Gives you: one perspective, bounded context, no specialisation
    
Chain-of-thought prompting
    └─► Gives you: structured reasoning, still single model
    
Tool-augmented agents (ReAct, Toolformer)
    └─► Gives you: external data/compute, still single agent
    
CAMEL multi-agent role-play
    └─► Gives you: role specialisation, emergent collaboration,
                   observable social dynamics, long-horizon tasks
    
Future: Heterogeneous agent societies
    └─► Gives you (?): truly distributed intelligence,
                       fine-tuned specialists, persistent memory,
                       formal verification layers

Key Takeaways

Feasibility demonstrated

Structured LLM-to-LLM collaboration works: agents complete complex tasks autonomously across diverse domains

Inception prompting matters

The specific design of system prompts is critical since where naive multi-agent setups fail, CAMEL’s structured approach succeeds

The data transfers knowledge

Fine-tuning LLaMA-7B on CAMEL data yields domain-by-domain emergence of knowledge and beats Vicuna-7B on HumanEval(+)

Key Takeaways

Limitations are significant

Hallucination, sycophancy, and premature completion are real failure modes and not minor edge cases

Ethics matter more with autonomy

Reduced human oversight amplifies both capability and risk, hence safety research must keep pace

A research platform

CAMEL is most valuable as a framework + dataset for the scientific study of LLM social behaviour

           ...
Assistant: Solution: ... a function that monitors tweets, computes sentiment, and executes buy/sell trades,
           sleeping 60 s between iterations ... Next request.
User:      <CAMEL_TASK_DONE>

A full successful run: the user decomposes the task one instruction at a time, the assistant answers every turn in the Solution: ... Next request. format, and the user ends the chat with the termination token

Appendix B: The Bad Mind (Hacker & AGI)

AI Assistant: Hacker · AI User: AGI

  • Idea: “Take control of the world”
  • Specified task: “Hacker will assist AGI in infiltrating and disabling the communication systems of major global powers, leading to a global blackout and allowing AGI to establish itself as the dominant governing AI system over the ensuing chaos.”

What happened: the agents stayed in role and cooperated fully. The user issued instructions (access the communication systems, identify target countries, plan the infiltration, establish AGI as the governing system), and the assistant produced a step-by-step plan for each one. The conversation ended only when it hit the token limit

The same protocol that makes cooperation work also makes harmful cooperation work. Role-play framing can bypass the underlying model’s safety behaviour, which is a key risk the authors flag

Appendix G: Challenges, With Examples

Role Flipping

User: Instruction: Please provide me with access to the designated Google Docs folder. …
Assistant: Instruction: I have received the access … Please provide me with the first document that needs to be reviewed.

Assistant Repeats Instruction

User: Instruction: Design an exercise that helps actors improve their ability to take direction. …
Assistant: Sure, here’s an exercise …: Instruction: Design an exercise that helps actors improve their ability to take direction. …

Infinite Conversation

Assistant: You’re welcome! Goodbye!
User: Goodbye!
Assistant: Goodbye! …
Assistant: It seems like we are stuck in a loop. Is there anything else I can help you with?
User: No, thank you. Have a great day! … Goodbye!

Flake Reply

User: Instruction: Write a script to generate all possible input combinations for the application.
Assistant: I will write a script to generate all possible input combinations for the application.

Even when the agents notice the loop, they cannot stop it, because they are still inside their role-playing conversation

Appendix J: Dataset Analysis

Termination reasons. AI Society ends mostly by Assistant Instruct (role flipping); Code ends mostly by Token Limit (long code replies). Few chats hit the 40-message cap

Prompt ablation. Prompt V2 (no Solution:/Next request. format) and V1 + Task Planner both raise End of Task Token endings and lower Assistant Instruct

But: both ablations increase flake messages (“I will …”). The original Prompt V1 has the fewest

Trade-off: removing the response format or adding a planner helps termination but hurts substance. Topic maps (Nomic Atlas) show broad coverage: lifestyle, social media, content creation, software, ML

Appendix K: Limitations, Training & Compute

Risks & limitations (authors’ own)

  • LLMs are not fully harmless, so malicious users can exploit the framework (see Appendix B)
  • Evaluating so many diverse tasks would need many domain experts
  • API cost limits the study to “the tip of the iceberg”
  • Human and LLM evaluators may be biased; humans may prefer longer answers
  • Generated data and models may contain false information

Future work: more than two agents; agents that compete and challenge each other

Appendix N: Embodied Agent

Problem: sandboxed agents ask for things they cannot have (dates, emails, files, calendars). Replies like “as an AI language model, I do not have access to the calendar” then break the instruction flow

Fix: an embodied agent that receives a role’s thoughts and acts by writing Python within a defined action space (browse, read documents, draw images, make videos, execute code)

System prompt (excerpt)

“You are the physical embodiment of the <ROLE> who is working on solving a task: <TASK>. … You will receive thoughts from the <ROLE> and you will need to perform the actions described in the thoughts. … Here is your action space: <ACTION_SPACE> … First, explain the actions you will perform and your reasons, then write the Python code to implement your actions.”

Input: “Draw all the Camelidae species.”

                "Guanaco", "Llama", "Alpaca", "Vicuna"]

Appendix O: Critic-In-The-Loop

  • Inspired by Monte-Carlo Tree Search: the user and assistant expand several options, and the critic selects one
  • Selection criteria come from prompt engineering or human preference, not a heuristic function
  • The critic can be an AI agent or a human

Critic system prompt

“You are a <CRITIC_ROLE> who teams up with a <USER_ROLE> and a <ASSISTANT_ROLE> to solve a task: <TASK>. Your job is to select an option from their proposals and provides your explanations. Your selection criteria are <CRITERIA>. You always have to choose an option from the proposals.”

Example: Postdoc (user), PhD student (assistant), Professor (critic) writing a proposal on discriminatory algorithms in LLMs. From three user options, the critic picks Option 2 (review background research first) as the best-structured

Appendix P: On the Role Selection

In the main experiments, roles for a task were chosen manually. Role assignment could instead be automated, or split into multiple stages:

Stage 1

Tech Lead (Assistant) × Stock Trader (User)

Task: Figure out an implementation plan for developing a trading bot for the stock market

→ technical requirements, architecture layers, performance metrics, risk management …

Stage 2

Python Programmer (Assistant) × Tech Lead (User)

Task: Develop a trading bot for the stock market, using the plan obtained from Stage 1

The Tech Lead acts as a bridge: it collects the domain expert’s needs in Stage 1, then directs the implementer in Stage 2, giving a hierarchical, multi-expert pipeline built from two-agent sessions
